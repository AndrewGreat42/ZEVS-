# Требования к CRM-системе ZEVS

## Назначение и границы MVP

Система используется авторизованными сотрудниками **одной** гостиницы через веб-браузер. CRM хранит номера, гостей и бронирования, проверяет доступность номера на интервал дат и показывает операционную сводку. Интерфейс на русском языке.

**Роли:** `ADMIN` (управление номерами, гостями и бронированиями) и `RECEPTIONIST` (просмотр номеров, работа с гостями и бронированиями). Управление учётными записями персонала включается как отдельная задача авторизации.

## Функциональные требования

Формулировки ниже описывают **конкретное наблюдаемое поведение**, критерии можно проверить тестами.

| ID | Требование: система должна… | Критерий проверки |
| --- | --- | --- |
| FR-01 | аутентифицировать сотрудника по логину и паролю | Верные данные → вход; неверные → HTTP 401 |
| FR-02 | ограничивать операции в соответствии с ролью | `RECEPTIONIST` не может изменять номера: HTTP 403 |
| FR-03 | показывать список номеров с номером, категорией, вместимостью, ценой и активностью | Возвращается список; доступен фильтр категории |
| FR-04 | разрешать `ADMIN` создавать и изменять карточку номера | После сохранения новые данные доступны; повторный номер отклоняется |
| FR-05 | создавать гостя с ФИО, телефоном и необязательным email | Создаётся запись с уникальным ID |
| FR-06 | искать гостя по части ФИО или телефона | Найдены записи, соответствующие запросу |
| FR-07 | показывать бронирования с номером, гостем, датами и статусом | Список фильтруется по статусу и датам |
| FR-08 | создавать бронь для существующего гостя и активного номера | При допустимых датах создаётся запись со статусом `PENDING` |
| FR-09 | предотвращать пересекающиеся неотменённые бронирования одного номера | Конфликтный запрос → HTTP 409, запись не создана |
| FR-10 | менять номер и даты брони до заселения | Изменение сохраняется, если новый период доступен |
| FR-11 | отменять бронь до заселения | `PENDING` или `CONFIRMED` → `CANCELLED` |
| FR-12 | подтверждать бронь | `PENDING` → `CONFIRMED` |
| FR-13 | отмечать заселение гостя | `CONFIRMED` → `CHECKED_IN` |
| FR-14 | отмечать выезд гостя | `CHECKED_IN` → `CHECKED_OUT` |
| FR-15 | показывать свободные номера на указанный интервал дат | Исключаются номера с пересекающимися действующими бронями |
| FR-16 | показывать количество активных номеров, занятых, заездов и выездов на заданную дату | Данные вычисляются из номеров и бронирований |
| FR-17 | вычислять и сохранять стоимость проживания | Количество ночей × цена номера за ночь на момент брони |
| FR-18 | позволять сотруднику завершать авторизованный сеанс | После выхода доступ к защищённым данным прекращается |

## Пользовательские сценарии

1. Администратор создаёт номер 101 с вместимостью 2 и ценой 3500 ₽/ночь.
2. Сотрудник добавляет гостя и находит свободный номер на 10–13 ноября.
3. Сотрудник создаёт бронь на 3 ночи; итоговая цена 10 500 ₽.
4. Сотрудник подтверждает бронь, регистрирует заезд и выезд.
5. При попытке второй брони того же номера на 12–14 ноября система отвечает конфликтом 409.

## Нефункциональные требования

| ID | Условие |
| --- | --- |
| NFR-01 | Данные хранятся в PostgreSQL, структура меняется через миграции Flyway |
| NFR-02 | Браузер взаимодействует с БД только через backend |
| NFR-03 | Пароли хранятся как криптографические хеши; реальные пароли не попадают в Git |
| NFR-04 | Сервер проверяет обязательные поля, диапазоны, даты и роли независимо от frontend |
| NFR-05 | Проверка пересечений действует при параллельных запросах на уровне БД |
| NFR-06 | Приложение может быть запущено локально по README |
| NFR-07 | Учебный стенд использует только синтетические данные гостей |

## Не входит в первую версию

Онлайн-оплата, каналы онлайн-бронирований, уведомления, динамическое ценообразование, CRM-маркетинг, программа лояльности, мобильное приложение и сеть отелей.

**Статус:** требования к согласованию с заказчиком / преподавателем, реализация запланирована.
