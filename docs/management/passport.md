## Обоснование
В малом отеле данные о гостях, номерах и бронированиях могут храниться в разрозненных таблицах. Это усложняет проверку дат и повышает риск двойного бронирования.

## Цель
Создать систему для работников одного малого отеля, обеспечивающую хранение информации о гостях, номерах и бронях, предотвращение пересечения бронирований, оформление заселения и выезда.

## Границы продукта
**Входит в MVP:** авторизация сотрудников, роли, справочник номеров, карточки гостей, поиск, управление бронями, проверка свободных дат, изменение статусов проживания, оперативная сводка.

**Не входит:** внешние площадки бронирования, платежи, CRM-рассылки, мобильное приложение, бухгалтерский учёт, несколько гостиниц.

## Технологии
Backend: Java 21, Spring Boot 3, Spring Security, Spring Data JPA. Frontend: JavaScript, React, Vite. БД: PostgreSQL 17, Flyway. Инфраструктура: GitHub, Issues/Projects, Docker Compose.

## Планируемые результаты
1. Требования, API-контракт, ER-схема и архитектура.
2. Git-репозиторий и система задач/учёта времени.
3. Локально запускаемая система со сквозным сценарием «гость → бронь → заселение → выезд».
4. Тесты критических бизнес-правил и демонстрация.

## Критерии успешности
- Все сценарии MVP работают при локальной демонстрации.
- Нельзя создать две пересекающиеся активные брони для одного номера.
- Разграничение прав по ролям работает.
- Инструкция запуска и документация актуальны.

## Риски
Дефицит времени, несовместимость API и UI, ошибки конкуренции при бронировании, проблемы локального окружения. См. [risks.md](risks.md).
